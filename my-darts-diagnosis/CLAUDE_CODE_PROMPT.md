# マイダーツ診断— Claude Code 用仕様書

このファイルは、Claude Code にそのまま渡して開発を始めるための仕様書です。
プロジェクトフォルダで Claude Code を起動し、このファイルの内容を最初の指示として貼ってください。

---

## 1. 作るもの

**「マイダーツ診断」公開版** — ダーツ初心者〜中級者が、12の質問に答えるだけで自分に合うバレル（ダーツの胴体部分）のスペックと、実際に買える製品候補が分かる、登録不要の無料Webアプリ。

- 想定ユーザー：初めてのマイダーツ選びで迷っている人、買い替えを考えている人
- 想定シーン：スマホで使う（ダーツバーやショップで立ったまま使う場面を含む）
- 公開方法：GitHub Pages（静的ホスティング）
- これは2026-11-14に作った個人用診断の「公開版・新規制作」。設計の骨格（質問と診断ロジック）は実績のある前回設計を土台にする

## 2. 技術条件（必須）

- **静的Webアプリ**。バックエンド、データベース、ビルドツールは使わない
- ファイル構成は次の3つ（＋任意でREADME）：
- `index.html` — 画面・デザイン・診断ロジック（HTML/CSS/JavaScript、外部ライブラリ不使用のバニラJS）
- `products.js` — 商品データ専用ファイル（後述）。ここだけ書き換えれば商品を差し替えられる構造にする
- `README.md` — 公開手順と商品データの更新方法
- フレームワーク、CDN、外部フォント・外部画像に依存しない（オフラインでも動くこと）
- **iPhone（Safari）／Android（Chrome）／PC（モダンブラウザ）のすべてで使えること**。端末ごとのネイティブアプリは作らず、Webアプリとして一本化する（URLを開くだけで使えるのが配布の強み）
- スマホ最優先のレスポンシブデザイン。PCでは中央寄せの読みやすい幅に収める
- 対応ブラウザ：最新の Safari / Chrome（モバイル含む）

## 3. 画面の流れ

1. **トップ画面**：タイトル「マイダーツ診断」、一文の説明、「診断をはじめる」ボタン。所要時間の目安（約1分）を表示
2. **質問画面**：1画面に1問。全12問。進捗表示（例：3 / 12 とプログレスバー）、「もどる」ボタンで前の質問に戻れる
3. **結果画面**：
- 推奨バレルスペック（模式図つき）
- おすすめセッティング（シャフト／フライト／チップ）
- 提案理由（なぜこのスペックなのかを平易な言葉で）
- 「この診断に近い販売中バレル」上位3本＋次点（最大3本）
- Xシェアボタン、結果コピーボタン、「もう一度診断する」ボタン
4. **重要なルール：診断が終わるまで、商品は一切表示しない**（トップ画面にも商品名・商品画像を出さない）

## 4. 質問（全12問・色の質問は入れない）

各問は選択肢タップで次へ進む形式にする。選択肢の文言は初心者にも分かる言葉にし、専門用語には短い補足を付ける。

| # | 質問項目 | 選択肢の方向性 |
|---|---|---|
| 1 | ダーツ歴・経験 | 初めて買う／数ヶ月／1年以上／買い替え検討中 |
| 2 | グリップ位置 | 前方／中央／後方／決まっていない |
| 3 | バレルの形の好み | トルピード（太めで短い）／ストレート（細くて長い）／樽型／分からない・おまかせ |
| 4 | 重さの好み | 軽め（〜18g）／標準（19〜20g）／重め（21g〜）／おまかせ |
| 5 | 長さの好み | 短め（〜44mm）／標準（45〜48mm）／長め（49mm〜）／おまかせ |
| 6 | 太さ（最大径）の好み | 細め（〜6.5mm）／標準（6.6〜7.0mm）／太め（7.1mm〜）／おまかせ |
| 7 | カットの種類 | リング／マイクロ／シャーク／複合／分からない |
| 8 | カットの強さ（掛かり） | 弱め（滑らか）／普通／強め（しっかり掛かる） |
| 9 | 重心の好み | フロント／センター／リア／おまかせ |
| 10 | 投げ方・飛ばし方 | 押し出す／振り抜く／落とすように／分からない |
| 11 | チップ規格 | 2BA（ソフト）／スティール／まだ決めていない |
| 12 | 予算とプレースタイル | 予算：〜¥8,000／〜¥15,000／〜¥25,000／上限なし ＋ スタイル：コントロール志向／飛びの安定志向／パワー志向（※1問にまとめるか2問に分けて全13問にしてもよいが、その場合は合計数を明記すること） |

## 5. 診断ロジック

- 回答から推奨スペックを決定する。出力は次の7項目：
- 形（トルピード／ストレート／樽型）
- 重さ（g、0.5g刻みの具体値）
- 全長（mm）
- 最大径（mm）
- 重心（フロント／セミフロント／センター／セミリア／リア）
- カット（種類＋強さ）
- タングステン率（90%／95% など）
- 「おまかせ／分からない」が選ばれた項目は、他の回答（グリップ位置、投げ方、プレースタイル、経験）から標準的な値を補完する。補完の考え方はコード内コメントに残す
- セッティング提案も併せて出す：
- シャフト長（mm表記＋ショート／インターミディエイト／ミディアム等の区分）
- フライト形状（スタンダード／シェイプ／スリム等）
- チップ（規格と代表的な系統名）
- 提案理由：回答のどれが効いたかを2〜4文で説明する（例：「中央グリップ＋押し出す投げ方なので、重心はフロント寄りが合います」）
- 参考：前回設計での実例 — 回答「トルピード／重め寄り／長さ中／太さ中／マイクロカット（普通）／フロント／中央グリップ／押し出す／2BA／予算中／コントロール志向」→ 結果「トルピード／20.5g／46.0mm／6.8mm／フロント／マイクロカット／90%＋シャフト40mm（インターミディエイト）／フライト スタンダード／チップ Premium Lippoint系」。この再現をテストケースに使う

## 6. 商品マッチング

- 結果画面でのみ、推奨スペックに近い実在バレルを適合度順に表示する
- 表示：上位3本をメイン、次点として最大3本を小さめに
- 各商品に付ける情報：製品名、メーカー、実スペック（形／重さ／全長／最大径／重心／カット／タングステン率）、価格（税込）、販売店名、販売ページへのリンク、**適合度（%）**、診断結果との「一致点／相違点」、データ確認日
- **売り切れ品は表示しない**（データ側の在庫フラグで除外）
- 適合度スコアの計算：形の一致を最重視し、重さ・全長・最大径は差が小さいほど高得点、重心とカットは一致度で加点。予算を超える商品は減点または次点送りにする。計算式はコード内コメントで説明する
- 検証方法：異なる2パターンの回答で表示される商品が変わること（動的マッチングであること）を確認する

## 7. 商品データ（products.js）

- 商品データは `products.js` に分離し、`const PRODUCTS = [ {...},...]` の形で保持する
- 1商品のフィールド：
- `name`（製品名）、`maker`（メーカー名）
- `shape`（torpedo / straight / barrel）、`weight`（g）、`length`（mm）、`maxDia`（mm）
- `balance`（front / semi-front / center / semi-rear / rear）
- `cut`（種類の文字列）、`cutLevel`（1=弱め〜3=強め）
- `tungsten`（%）、`tip`（"2BA" 等）
- `price`（税込・円）、`shop`（販売店名）、`url`（販売ページURL）
- `inStock`（true/false）、`checkedAt`（"YYYY-MM-DD"）
- **⚠ データの正確性について（最重要）**：
- 価格・在庫は変動する情報。前回（2026-11-14）時点の商品プールや価格メモが存在するが、**古い価格・在庫を事実として埋め込んではいけない**
- 初期データは「形式のサンプル」として数件だけ入れ、各レコードの `checkedAt` と画面注記で古い情報だと分かるようにする。**本公開の前に全商品の再検証（価格・在庫・URL）が必要**であることを README に明記する
- 画面の商品欄の近くに「価格は各商品の確認日時点のものです。最新の価格・在庫は販売ページでご確認ください」と注記を表示する

## 8. Xシェア機能

- 結果画面に「結果をXでシェア」ボタンを置く
- 投稿文は自動生成：診断結果の要約（形・重さ・全長・重心）＋アプリURL＋ハッシュタグ（例：#マイダーツ診断）
- 例：「マイダーツ診断の結果はでした🎯 あなたに合うバレルは？ #マイダーツ診断 （URL）」
- `https://twitter.com/intent/tweet?text=...` の Web Intent 形式で開く（URLは公開先が決まったら差し替えられるよう、定数1か所にまとめる）
- 「結果をコピー」ボタンも付ける（シェアしない人向け）

## 9. デザイン

- ダーツバーの雰囲気：ダーク（チャコール〜黒）基調＋真鍮／ゴールドの差し色。結果画面のスペック模式図はシンプルなSVGで描く
- **文字サイズは標準**（大きくしすぎない）。読みやすさは余白とコントラストで確保する
- カード型レイアウト、説明文は短く。質問の選択肢はタップしやすい大きさ（高さ48px以上）
- 進捗バー、結果の適合度表示など、状態が一目で分かること

## 12. 完成条件（セルフチェック）

開発の最後に、次をすべて確認して報告すること：

- [] トップ→12問→結果まで一通り流れる（途中で詰まらない、もどるボタンが効く）
- [] 診断が終わる前に商品が一切表示されない
- [] テストケース（5章の実例の回答）で、期待に近いスペックが出る
- [] 回答パターンを変えると、推奨スペックと商品マッチングの両方が変わる
- [] 売り切れ（inStock: false）の商品が結果に出ない
- [] Xシェアボタンの投稿文に結果サマリーとハッシュタグが入る
- [] スマホ幅（375px程度）でレイアウトが崩れない
- [] iPhone Safari／Android Chrome／PCブラウザのいずれでも、質問→結果→シェアまで同じように動く
- [] 価格の注記（確認日時点）とデータ出典の注記が結果画面にある
- [] products.js だけを書き換えて商品が差し替わる（index.html を触らずに済む）
